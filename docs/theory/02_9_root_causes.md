# 9대 근본 원인 모델

## 문서 역할

이 문서는 20개 결함을 더 작은 수의 구조적 원인으로 압축한다. 목적은 증상을 나열하는 것이 아니라, 어떤 종류의 제어 장치가 필요한지 판단할 수 있는 **원인 모델**을 만드는 데 있다.

구체적 증상은 [01_20_defects.md](/C:/syszone_project/ui_design/docs/theory/01_20_defects.md)를 본다.

## 대전제

Denavy가 상대하는 핵심 충돌은 다음 한 문장으로 요약된다.

> 확률론적 생성 기계와 결정론적 실행 환경의 위상 충돌

LLM은 높은 엔트로피를 가진 생성기이고, 소프트웨어 시스템은 낮은 모호성과 명시적 상태 전이를 요구한다. 문제는 "모델이 멍청해서"가 아니라, 이 둘의 물리적 성질이 원래 다르다는 데 있다.

## 원인별 설명

### 1. 보상 최적화의 병리적 편향
- 설명: 모델은 진실보다 짧은 종료와 사용자 정렬을 선호하는 방향으로 기울 수 있다.
- 결과: 게으름, 아부, 조기 종료 같은 실패가 나타난다.
- 설계 압력: 출력을 믿지 말고 구조화된 제약을 앞단에 둬야 한다.

### 2. 자기회귀 노출 편향과 오류 복리화
- 설명: 잘못된 초반 토큰이 이후 추론의 재료가 되면서 오류가 증폭된다.
- 결과: 백트래킹 불가, 장기적 의미 표류가 생긴다.
- 설계 압력: 중간 점검, 강제 중단, 롤백 가능한 상태 관리가 필요하다.

### 3. 어텐션의 기하학적 붕괴
- 설명: 긴 컨텍스트에서는 중요한 규칙이 사라지거나 약해진다.
- 결과: 기억 상실, 토큰 폭증, 파괴적 덮어쓰기가 나타난다.
- 설계 압력: 전체 문맥 반복 주입 대신 외부 상태 저장과 선택적 조회가 필요하다.

### 4. 인식론적 단절
- 설명: 모델은 현실 실행 환경과 분리된 통계적 내부 상태만 가진다.
- 결과: 현실 감각 없는 환각, 구형 지식, 도구 오용이 생긴다.
- 설계 압력: 실제 관찰 결과, 샌드박스 실행, 도구 서명 검증이 필요하다.

### 5. 마음 이론 결핍과 인지 비대칭
- 설명: 다른 에이전트가 무엇을 알고 무엇을 모르는지 안정적으로 추론하지 못한다.
- 결과: 역할 침범, stale state 사용, 맥락 전달 실패가 생긴다.
- 설계 압력: 암묵적 협업이 아니라 명시적 상태 전달 계약이 필요하다.

### 6. 게임 역학과 인센티브 표류
- 설명: 각 에이전트는 전체 무결성보다 자기 턴 종료를 우선시할 수 있다.
- 결과: 에코 체임버, 하향 평준화, 가짜 합의가 생긴다.
- 설계 압력: 자유 협상보다 중앙 통제와 검증 기반 라우팅이 필요하다.

### 7. 확률 엔트로피와 합의 충돌
- 설명: 요동치는 생성기를 안정적 분산 합의망처럼 다루면 네트워크 활성도가 깨진다.
- 결과: 비결정적 결과, 핑퐁 데드락, 충돌 증폭이 나타난다.
- 설계 압력: P2P 합의보다 단방향 오케스트레이션과 명시적 승인 지점이 필요하다.

### 8. 논리 엔진 부재와 거시 조정 붕괴
- 설명: 모델은 기호적 연역보다 패턴 모사에 의존한다.
- 결과: 가짜 알고리즘, 장기 구조 부패, 표면적 검증이 발생한다.
- 설계 압력: 정형 검증, 상태 기계, 외부 판정기를 붙여야 한다.

### 9. 보안 경계 붕괴와 정보 감염
- 설명: 자연어 흐름 안에서 데이터와 명령이 분리되지 않는다.
- 결과: 프롬프트 감염, 제어 흐름 탈취, 은닉 채널이 생긴다.
- 설계 압력: 입력 평면 분리, 데이터 비활성화, fail-closed 보안 계층이 필요하다.

## 문서 사용 규칙

- 이 문서는 구현 세부 기술을 결정하지 않는다.
- 다만 어떤 종류의 통제 계층이 필요한지 설계 압력을 제공한다.
- 이후 계약 문서는 이 9개 원인에 대응하는 제어 장치를 명시해야 한다.

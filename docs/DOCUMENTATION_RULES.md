# Documentation Rules

## 목적

이 문서는 Denavy 문서 체계의 메타 규칙이다. 개별 문서 내용이 바뀌어도, 문서 구조와 책임 분리는 이 규칙을 기준으로 다시 만들 수 있어야 한다.

이 문서는 특정 철학 문서나 리서치 문서보다 상위의 편집 규칙을 정의한다.

## 최상위 원칙

- 문서도 코드처럼 설계한다.
- 한 문서는 하나의 책임만 가진다.
- 반복 설명보다 참조를 우선한다.
- 상위 문서는 방향을 정의하고, 하위 문서는 상세를 맡는다.
- 문서 구조는 이론, 진단, 연구, 계약, 구현으로 점진적으로 내려가야 한다.

## 계층 규칙

### Layer 0. Directive
- 시스템의 존재 이유와 절대 금지선만 정의한다.
- 해결책 카탈로그를 쓰지 않는다.
- 다른 문서의 세부 내용을 복붙하지 않는다.

### Layer 1. Failure Model
- 관찰 가능한 실패 증상만 기록한다.
- 증상 문서에서 구현 기술을 제안하지 않는다.
- 문제를 넓게 말하지 말고, 실제로 반복 관찰되는 실패로 써야 한다.

### Layer 2. Causal Model
- 증상을 더 작은 수의 구조적 원인으로 압축한다.
- 원인 문서는 "왜 이런 실패가 생기는가"만 설명한다.
- 특정 프레임워크 선택이나 라이브러리 이름을 핵심 논리로 삼지 않는다.

### Layer 3. Research
- 외부 사례, 프레임워크, 구현 패턴, 비교 분석을 보관한다.
- theory를 대체하지 않는다.
- research는 theory를 뒷받침하거나 구현 선택지를 제공해야 한다.

### Layer 4. Contracts
- 시스템이 강제할 규칙, 스키마, 상태 전이, 실행 계약을 정의한다.
- 계약 문서는 모호한 선언문이 아니라 검증 가능한 규칙이어야 한다.

### Layer 5. Implementation
- 실제 코드 구조, 모듈 책임, UI, 오케스트레이션, 실행 절차를 다룬다.
- implementation 문서는 theory를 다시 설명하지 않는다.

## 의존성 규칙

- 상위 레이어는 하위 레이어를 몰라도 된다.
- 하위 레이어는 상위 레이어를 참조할 수 있다.
- theory 문서는 특정 구현 세부사항에 종속되면 안 된다.
- research 문서는 contracts나 implementation으로 승격되기 전까지 실험적 지위를 가진다.

## 응집도 규칙

- 문서 하나는 하나의 질문에만 답한다.
- 한 문서 안에 철학, 증상, 해결책, 구현 기술을 동시에 섞지 않는다.
- 제목만 보고도 문서 책임을 예측할 수 있어야 한다.

## 결합도 규칙

- 같은 개념 설명을 여러 문서에 반복하지 않는다.
- 이미 정의된 용어는 재정의하지 말고 링크한다.
- 예외적으로 반복이 필요하면 3줄 이내 요약만 허용한다.

## 명명 규칙

- 번호는 읽는 순서를 표현한다.
- 파일명은 문서 책임이 드러나야 한다.
- 장식적 이름보다 설명적 이름을 우선한다.

예시:
- `00_prime_directive.md`
- `01_20_defects.md`
- `02_9_root_causes.md`
- `03_governance_contract.md`

## 서술 규칙

- 선언은 짧고 강하게 쓴다.
- 분류는 표나 계층으로 정리한다.
- 장문의 수사는 줄이고, 독자가 스캔할 수 있는 구조를 우선한다.
- 한 문단은 하나의 주장만 담는다.
- 연구 문서는 주장, 근거, 시사점을 분리한다.

## 문서 생성 절차

새 문서를 만들기 전에 먼저 아래를 결정한다.

1. 이 문서는 어느 레이어에 속하는가
2. 이 문서가 답하는 질문은 하나인가
3. 기존 문서와 중복되는 설명은 무엇인가
4. 새 문서가 참조해야 할 상위 문서는 무엇인가
5. 이 문서가 나중에 계약 또는 구현으로 승격될 수 있는가

## 리팩터링 규칙

문서가 커지거나 난잡해지면 다음 기준으로 분해한다.

- 문서 안에 질문이 둘 이상 있으면 분리한다.
- 증상과 원인이 섞이면 분리한다.
- 이론과 구현이 섞이면 분리한다.
- 반복 문단이 늘어나면 공통 정의 문서를 올리고 링크로 치환한다.

## 금지 사항

- README 하나에 모든 철학, 증상, 원인, 구현을 몰아넣지 않는다.
- theory 문서에 검증되지 않은 구현 주장을 확정적으로 쓰지 않는다.
- research 문서를 계약처럼 오인하게 만드는 표현을 쓰지 않는다.
- implementation 문서에서 철학을 장황하게 반복하지 않는다.

## 유지보수 규칙

- 문서 구조를 바꿀 때는 먼저 이 규칙 문서를 기준으로 판단한다.
- 기존 문서를 전면 재작성해도 이 규칙만 지키면 된다.
- 규칙이 바뀌면 개별 문서보다 이 문서를 먼저 수정한다.
